# X1 — Web UI

Une interface web locale (React, servie par FastAPI) donne accès à tout ce que fait l'agent, sans terminal : la réponse en streaming, la requête SQL et ses résultats, les étapes de l'agent, la confirmation des actions destructives et le verdict du juge. Elle ne contient aucune logique métier : elle affiche les événements du moteur et lui transmet les actions de l'utilisateur, par un seul WebSocket.

Chaque critère est relié à un test ou à une étape de démo (actes de [`docs/keynote/scenario.md`](../keynote/scenario.md)). Deux familles de tests :
- côté serveur, `pytest <chemin>::<test>`, lancé par la CI ;
- côté navigateur, Vitest (`cd web && npm test`), noté `web/src/<fichier> › <describe> › <it>`. Ces tests rejouent les mêmes fixtures que le `MockEngine` (`tests/fixtures/events/`). **Ils ne tournent pas encore dans la CI** (job front à ajouter).

Tâches : WEB-02 (squelette), WEB-04 (WebSocket et `MockEngine`), WEB-05 (chat), WEB-06 (SQL, résultats, timeline), WEB-07 (modale HITL), WEB-08 (moteur réel), WEB-09 (badge du juge), WEB-10 (barre d'état), WEB-11 (panneau mémoire), WEB-13 (finitions et réglages), WEB-14 (build de production) ; WEB-12 (timeline complète) a été coupée (D-05). Les panneaux des autres fonctionnalités ont leurs propres stories : profils [A5](A5.md) (WEB-15), questions [X4](X4.md) (WEB-16), note du comité [M4](M4.md) (WEB-17), export et partage [X3](X3.md), tâches planifiées [X5](X5.md). Contrat : [`docs/contracts/websocket.md`](../contracts/websocket.md). La modale de confirmation et le badge du juge sont aussi décrits du point de vue de leur fonctionnalité dans [A3](A3.md) et [EV1](EV1.md).

## US-X1-01
En tant que **contrôleuse de gestion**, je veux **poser une question métier dans mon navigateur et voir la réponse, la requête SQL et les résultats**, afin d'**obtenir un chiffre fiable sans écrire de SQL ni utiliser de terminal**.

**Critères d'acceptation**
- La réponse s'affiche progressivement pendant la génération.
  — vérifié par : `tests/unit/web/test_ws.py::test_a_turn_replays_contract_events`, `tests/unit/web/test_real_engine.py::test_a_turn_on_the_real_engine` (les fragments `token` arrivent avant `message_done`) ; `web/src/session/reducer.test.ts › replaying the fixtures › act 1: question, tool calls, answer, usage and judge` et `› batched and one-by-one dispatches give the same state` (un rendu par image, quel que soit le nombre de fragments reçus) ; démo : acte 1.
- Le SQL exécuté est consultable et copiable depuis le message.
  — vérifié par : `web/src/session/steps.test.ts › nominal fixture (act 1) › shows only the corrected query under the answer, with its table` (la requête qui a tourné est sous la réponse, l'essai raté reste dans la timeline) ; `web/src/sql/highlight.test.ts › layoutSql › only changes whitespace` (la coloration ne modifie pas la requête, le bouton Copier copie l'original) ; démo : acte 1, bloc SQL « lecture seule », Copier puis « Voir les résultats ».
- Les lignes de résultat s'affichent dans un tableau triable.
  — vérifié par : `web/src/results/table.test.ts › sortRows` (nombres triés comme des nombres, ordre alphabétique français, valeurs vides toujours en bas, cycle croissant / décroissant / ordre du serveur) ; `› asRowSet › never keeps more than row_limit rows` (200 lignes au plus, mention « résultat tronqué » sans total inventé) ; `› formatCell` (format français, mêmes décimales sur toute la colonne) ; démo : acte 1, clic sur l'en-tête `delai_moyen_jours`.
- Une panne est expliquée sans écran vide : erreur d'Ollama avec la commande à lancer, bandeau « reconnexion en cours » quand le serveur ne répond plus, et message clair si le serveur a redémarré entre-temps (la conversation n'a pas pu être reprise).
  — vérifié par : `web/src/session/reducer.test.ts › session messages › says so when a reconnection finds a server that lost the conversation`, `› errors outside a turn become notices, three at most` ; `web/src/shared/inlineCode.test.ts › codeParts` (« lancez `ollama serve` » affiché comme une commande) ; démo : arrêter puis relancer `sensai web` pendant une conversation.

**Statut** : fait (WEB-05, WEB-06, WEB-08, WEB-13)

## US-X1-02
En tant qu'**admin IT**, je veux **changer de modèle et voir la consommation du contexte depuis l'interface**, afin de **diagnostiquer une lenteur ou une réponse tronquée**.

**Critères d'acceptation**
- La liste des modèles provient d'Ollama.
  — vérifié par : `tests/unit/web/test_real_engine.py::test_models_and_their_tool_support` (noms lus dans Ollama, avec la prise en charge des outils), `tests/unit/web/test_real_engine.py::test_ollama_down_gives_no_model_instead_of_an_error`, `tests/unit/web/test_server.py::test_models_lists_the_default_and_the_tool_support` (`GET /api/models`) ; `web/src/statusbar/status.test.ts › models` (taille du modèle, mention « sans outils », modèle courant toujours dans la liste) ; démo : sélecteur « Modèle » de la barre d'état.
- Le changement s'applique au tour suivant sans perdre l'historique.
  — vérifié par : `tests/unit/web/test_ws.py::test_set_model_and_set_config_are_acknowledged` (message `set_model`, réponse `model_changed`), `tests/unit/web/test_real_engine.py::test_the_judge_follows_the_agent_model_unless_it_has_its_own` ; `web/src/session/reducer.test.ts › session messages › applies a model change and a config change` (la conversation affichée est conservée) ; démo : changer de modèle dans la barre d'état, la conversation reste à l'écran et la question suivante part sur le nouveau modèle.
- La jauge tokens utilisés / taille du contexte se met à jour après chaque réponse.
  — vérifié par : `web/src/session/reducer.test.ts › replaying the fixtures › act 1: question, tool calls, answer, usage and judge` (la jauge suit `message_done.usage`), `› turn status › an interrupted answer keeps its text and the previous context gauge`, `› session messages › a reset empties the conversation and the gauge, then ignores late events` ; `web/src/statusbar/status.test.ts › gauge` (orange à 75 %, rouge et « dépassé » au-delà de 100 %) ; démo : barre d'état « Contexte : 3 412 / 8 192 ».
- Tous les réglages de session (température, fenêtre de contexte, juge activé, modèle du juge) se changent depuis le menu « Réglages », pour la conversation seulement : `config.toml` n'est jamais modifié, et « Réinitialiser » revient à ses valeurs. Le reste de la configuration est affiché en lecture seule.
  — vérifié par : `tests/unit/web/test_server.py::test_config_gives_the_settings_of_the_interface` (`GET /api/config` : valeurs de `config.toml`, bornes, aucun chemin ni commande), `tests/unit/web/test_ws.py::test_set_model_and_set_config_are_acknowledged` ; `web/src/statusbar/settings.test.ts › settings (X1, set_config)` (tailles de contexte proposées, réinitialisation des seuls réglages modifiés) ; démo : Réglages, fenêtre de contexte à 16 384, la jauge affiche « / 16 384 » tout de suite.

**Statut** : fait (WEB-08, WEB-10, WEB-13)

## US-X1-03
En tant que **contrôleuse de gestion**, je veux **suivre les étapes de l'agent pendant qu'il travaille**, afin de **comprendre d'où vient le chiffre**.

**Critères d'acceptation**
- Chaque appel d'outil apparaît dans une timeline avec son statut et sa durée.
  — vérifié par : `web/src/session/steps.test.ts › nominal fixture (act 1) › has one timeline line per tool call, with the failed attempt visible`, `› shows a step as running until its result arrives`, `› formatDuration › uses ms below one second, then seconds in French` ; démo : acte 1, panneau Timeline (`time · get_current_time`, `sql_toolbox · run_select`, puis la vérification du juge).
- Une erreur d'outil est visible et expliquée.
  — vérifié par : `web/src/session/steps.test.ts › nominal fixture (act 1) › has one timeline line per tool call, with the failed attempt visible` (l'erreur `no such column: m.margin` reste affichée, l'essai corrigé suit), `› errors fixture › marks every attempt as failed when the agent gives up`, `› HITL fixtures › waits for the confirmation, then shows the refused write` (une écriture refusée est marquée « refusée », pas « erreur »).
- La timeline reste consultable après la réponse.
  — vérifié par : `web/src/session/steps.test.ts › nominal fixture (act 1) › links the message to its steps` (le lien « 5 étapes · 4,1 s » de chaque message ouvre son tour dans la timeline) ; démo : après l'acte 2, revenir au tour de l'acte 1 depuis son message.

**Statut** : fait (WEB-06). La timeline complète (arguments complets, « Tout replier », compteur d'auto-corrections, WEB-12) a été coupée (D-05) : la timeline actuelle montre déjà chaque appel, son résultat et sa durée.
